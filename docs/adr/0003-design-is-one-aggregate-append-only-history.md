# A Design is one aggregate, and its history is append-only

The PRD proposes nine tables, three of which (`designs`, `specifications`, `creative_directions`) are 1:1 and always read together. v1 collapses them into a single `designs` row and keeps a separate append-only `design_events` table (`status_change` | `decision` | `edit` | `note`) instead of the PRD's `design_revisions` and `design_decisions`. Only Category, Collection, Image, Material, and Event are separate tables. Material is separate because it repeats: a design uses several fabrics, where the rest of the specification is singular. Rationale: one atomic write per save, and search over "materials + mood + collection" becomes one column instead of three joins — which is exactly the PRD's own search requirement. Events merge too because changing status to Rejected *is* recording a reason; two tables would make the owner write the same thing twice.

## Consequences

- Sectioned forms are a UI concern only; they do not imply separate storage.
- Automatic edits are one event per editing session carrying a field diff, recorded silently. Nothing prompts, nothing announces a save — the owner opens a History screen when they want to know what changed.
- Because events are immutable, §8's "changes should not silently overwrite historical decision records" is satisfied structurally.
- Soft delete on designs doubles as a sync tombstone, so UUID primary keys plus `updated_at` make a future sync addable without rewriting foreign keys. Tombstones were not built; they fall out of deletion.
- The event diff is the only protection against overwriting a field: soft delete covers deletion, nothing else covers a destructive edit.
- **Six statuses, not the PRD's seven.** §4.6's Prototype status is cut: a physical sample can exist while the design is still In Development, so the two facts cannot share one value, and alternating between them writes churn into the History. Samples are recorded as `prototype` images. This is a deliberate deviation from the PRD, not an omission.

## Amendments

- **#27, amended by #29 — Material uses.** A design's Materials repeat, so a use lives in `design_materials`: one design's use of a Material, with the colour and the role (main, secondary, other). It is a sixth separate table beside the ones named above, and it holds no name of its own — the Material does. A use added, removed, or corrected during an editing session is part of that session's one Event: the diff's `materials` key carries the added, removed, and corrected uses alongside the fields it changed, and the visit hands them over as one `materialUses: { before, after }` pair on `recordEdit`. Rows written before the key existed carry their uses under the old `materialUses` key; the read translates them into `materials.added`, so they render as added uses.

- **#48, amended by #63 — Images are their own table, and `image_change` is a fifth Event kind.** A design's Images repeat, so an Image lives in `images`: one design's Image, with the kind it plays in the journey (`inspiration`, `sketch`, `prototype`, or `final`), its file's content hash, and that file's extension. The file itself stays outside the catalog, in the image store, under its hash and extension; the catalog holds the key. The kind is a label, not history — an Image can be reclassified as the design changes. An Image action writes its Event immediately, not at the close of a Visit: the one write path — attach, reclassify, or remove — appends one Event of kind `image_change` per action, and the diff's `images` key carries the Images it `attached`, `removed`, or `reclassified`. An attach of several files is one action, so one Event carries several `attached` entries. The stored file of an Image whose last reference goes is released in the same transaction, and the row write is the truth: a store that refuses the release leaves the file behind — the store's failure, not the write's — so no release can make the write fail. The Cover is derived from the Images on every read and never stored, so a reclassification changes it with no other act. The event kinds are now `status_change` | `decision` | `edit` | `note` | `image_change`; this line supersedes the four named above.

- **#51 — Image notes are their own table, and they die with their Image.** An Image's commentary repeats, so an Image note lives in `image_notes`: one note's text bound to the Image it explains. Adding or removing one goes through the one image write path and moves the design's `updatedAt` in the same transaction, but records no Event — History records the Image's life, not the note's. A removed Image takes its notes with it inside that same delete, silently, so no note outlives the picture it explains.
